# 我平时怎么和 AI 一起工作

很多时候，我开始一个任务时只有一些直观感受：这个地方不太好用，那个逻辑我还没弄明白，或者我觉得一个东西还可以更好看一点。我会先把这些感受告诉 AI，一起讨论，再决定具体做什么。

下面是我使用这套工具时的一些习惯。如果你也有类似的问题，可以参考一下。

## 先把问题和想法说出来

我通常会先描述当前的情况、遇到的问题，以及自己希望达到的效果。如果有几个问题，就分条列出来，再请 AI 给出分析和建议。

这个阶段，我希望先知道方案为什么这样设计，还有没有没想清楚的地方。对于不容易理解的过程，我也会请它画图，或者做一个临时 HTML，帮助我弄懂原理。觉得方向合适了，再把范围、限制和验收要求写清楚，形成可以继续实施的 plan。

准备开始时，用 dynamic-skills 为当前项目选择需要的 skill。先看这个项目要做什么，再决定安装哪些，已有项目的技能选择和版本也要保留。

## 实施时，看看各个 agent 在做什么

我用 Herdr 按项目组织终端，Radar 在侧栏显示 agent 的状态。哪个还在工作，哪个需要我回复，哪个已经完成，可以先从这里看。

Pi 这边，block editor、HUD 和其他扩展分别负责输入、状态和工具输出。羊皮纸主题让几个常用工具的配色更接近，成功、警告和错误也尽量使用一致的颜色。

如果要让另一个 agent 接手一部分工作，我会先写清楚它能改哪些文件、要交付什么，以及怎么验收。cd-connect 可以把这样的任务交给 DSH Desktop，执行端仍然使用自己的模型、权限和审批设置。并行工作时，还需要避免几个 agent 同时改同一处。

## 文档写出来之后，再读一遍

方案或调研结果需要保存成文档时，我希望它离开当前聊天之后也能读懂。结论、理由、来源和还没解决的问题都要写清楚，读起来费劲的地方，再用 plain-docs 检查一下。

conv-docs 解决的是阅读的问题：把明确选中的文档提供预览，离开电脑后，也可以在手机上继续看。读完有疑问，再回来继续讨论，不用一直在终端里翻聊天记录。

## 做完之后，回到原来的问题检查

AI 说完成了之后，我会再对照最初的需求和方案看一遍：具体改了什么，原来的问题是否解决，相关测试有没有通过，还有哪些没有验证。

这里要分清几件事。代码检查通过了，不一定代表真实账号已经可用；离线测试完成了，也不一定代表手机上的实际显示正常。检查结果要能说明这次到底验证到了哪一步，别把以前通过的结果直接当作这次通过。

另外，别把已有的工作改丢了。改动涉及版本或配置时，把为什么这样选、出了问题怎么恢复也记下来，下次再调整时可以接着看。

目前我大致是这样用的。这些工具和做法都还会继续调整，你可以按自己的项目来选，不需要照着全部装一遍。
